¿De qué trata la aplicación?

NEXUS LIVE es un sistema de venta de entradas para un evento musical (AURORA WORLD TOUR). Hay 180.000 personas esperando y solo 42.000 entradas. El problema: el motor de reservas anterior no era confiable y permitía que dos personas compraran el mismo asiento.

Esta aplicación reconstruye el motor desde cero. Garantiza que un asiento pase de AVAILABLE a HELD y luego a SOLD sin que nunca se venda a dos personas diferentes.

2. Interfaz (NEXUS Control Room)

Al abrir el navegador verás:

  • Mapa de asientos: cuadrículas verde (disponible), amarillo (reservado), rojo (vendido).
  • Selector de usuario: escribe qué usuario está comprando.
  • Botón RESERVAR: crea una reserva temporal de los asientos seleccionados.
  • Botón PAGAR: confirma la compra. Debajo hay un selector de escenario para elegir cómo responde el pago.
  • Botón SIMULAR CARRERA: lanza N usuarios simultáneos sobre un mismo asiento para demostrar que solo uno gana.
  • Botón SIMULAR UNA RESERVA: flujo guiado de un clic para jueces.
  • Panel de trazabilidad: historial de cambios de estado de la reserva.
  • Panel de recurrencia: estado de las cuotas si se pagó con RECURRENCE.

Debajo del botón PAGAR hay un menú desplegable:

Estados de un asiento

Un asiento solo puede estar en uno de tres estados. Las transiciones están controladas por el servidor:

stateDiagram-v2 [*] --> AVAILABLE AVAILABLE --> HELD: crear reserva HELD --> AVAILABLE: expira / libera / pago rechazado HELD --> SOLD: pago aprobado SOLD --> [*]
Regla clave: nunca se puede pasar de AVAILABLE directamente a SOLD. Siempre debe haber un HELD intermedio. Y nunca dos HELD al mismo tiempo para el mismo asiento.

Concurrencia: cómo se evita el doble venta

El problema

Si 100 personas intentan reservar el mismo asiento al mismo tiempo, el sistema debe garantizar que exactamente una lo consiga. No dos. No "casi siempre una".

La solución: Cola + Transacción atómica

flowchart LR A[100 solicitudes simultáneas] --> B[Cola de 50 sesiones] B --> C[Procesa de a 50] C --> D["BEGIN IMMEDIATE (lock de escritura)"] D --> E["¿Asiento AVAILABLE?"] E -- Sí --> F["Marcar HELD + COMMIT"] E -- No --> G["RECHAZADO + ROLLBACK"] F --> H[1 ganador] G --> I[99 rechazados]

Cola de 50 sesiones (punto dulce):

  • Todas las peticiones pasan por una cola que permite máximo 50 procesándose a la vez.
  • Si hay más de 50, las restantes esperan. Si esperan demasiado, se rechazan con 503 SERVICE_BUSY.
  • Esto evita que el sistema se degrade por sobreconsumso.

Transacción BEGIN IMMEDIATE:

  • SQLite adquiere el lock de escritura antes de leer el estado del asiento.
  • Si dos hilos compiten, el segundo espera hasta que el primero haga COMMIT o ROLLBACK.
  • Al re-ejecutar, el asiento ya está HELD → se rechaza.

Simulación de carrera (sequence diagram)

sequenceDiagram participant U1 as Usuario 1 participant U2 as Usuario 2 participant Q as Cola (50) participant DB as SQLite U1->>Q: reservar VIP-A-001 U2->>Q: reservar VIP-A-001 Q->>DB: BEGIN IMMEDIATE (U1) Q->>DB: BEGIN IMMEDIATE (U2 espera) DB-->>U1: asiento AVAILABLE → marcar HELD U1->>DB: COMMIT DB-->>U2: lock liberado, re-intentar Q->>DB: BEGIN IMMEDIATE (U2) DB-->>U2: asiento HELD → RECHAZADO U2->>DB: ROLLBACK

Circuit Breaker (proveedor de pagos inestable)

Cuando el proveedor de pagos falla repetidamente, el Circuit Breaker protege al sistema:

stateDiagram-v2 [*] --> CLOSED CLOSED --> OPEN: 3 fallos consecutivos OPEN --> HALF_OPEN: después de 15 segundos HALF_OPEN --> CLOSED: 1 llamada de prueba exitosa HALF_OPEN --> OPEN: 1 llamada de prueba fallida
Cuando el CB está OPEN, las confirmaciones reciben 503 PAYMENT_SERVICE_UNAVAILABLE y el asiento no se marca como SOLD. Así nunca se vende sin certeza del pago.

Historias de usuario

HU-1: Reservar asientos

Como comprador, quiero seleccionar asientos y reservarlos temporalmente, para asegurarlos mientras decido pagar.

Criterios de aceptación:

  • Puedo seleccionar 1 o más asientos disponibles.
  • Si todos están disponibles, se crea la reserva (HOLD).
  • Si alguno no está disponible, la reserva falla completa (todo o nada).
  • No puedo tener más de 6 asientos reservados a la vez.
  • La reserva expira automáticamente después de 120 segundos.

HU-2: Confirmar compra

Como comprador, quiero confirmar mi reserva con un pago, para finalizar la compra.

Criterios de aceptación:

  • Puedo elegir el escenario de pago (aprobado, rechazado, error, timeout).
  • Si el pago es aprobado, los asientos pasan a SOLD.
  • Si el pago es rechazado, los asientos vuelven a AVAILABLE.
  • Si hay error o timeout, los asientos se mantienen HELD y puedo reintentar.

HU-3: Concurrencia segura

Como sistema, quiero garantizar que dos usuarios no reserven el mismo asiento, para evitar sobreventa.

Criterios de aceptación:

  • Si 100 usuarios piden el mismo asiento, exactamente 1 lo consigue.
  • Los 99 restantes reciben un rechazo claro.
  • No hay overselling (0 ventas duplicadas).

HU-4: Idempotencia (reintentos seguros)

Como cliente móvil, quiero reintentar una operación sin efectos secundarios, para no crear reservas duplicadas.

Criterios de aceptación:

  • Si envío la misma solicitud con la misma Idempotency-Key, obtengo el mismo resultado.
  • Si envío una solicitud diferente con la misma clave, recibo un conflicto (409).

HU-5: Pago recurrente (cuotas)

Como comprador, quiero pagar en cuotas, para diferir el pago de mis entradas.

Criterios de aceptación:

  • Al confirmar con RECURRENCE, se crea un plan de 3 cuotas.
  • La primera cuota se cobra al confirmar.
  • Puedo simular el cobro de las siguientes cuotas desde la UI.

HU-6: Juez simula una reserva

Como juez, quiero probar el sistema sin usar curl ni Postman, para verificar los escenarios del reto.

Criterios de aceptación:

  • Puedo ver el mapa de asientos con colores.
  • Puedo reservar y pagar desde la interfaz.
  • Puedo simular una carrera de múltiples compradores.
  • Puedo simular una reserva completa con un solo clic.
  • Puedo ver la trazabilidad de cada reserva.

HU-7: Trazabilidad

Como operador, quiero ver el historial de cambios de estado de una reserva, para explicar por qué un asiento terminó AVAILABLE, HELD o SOLD.

Criterios de aceptación:

  • Cada cambio de estado se registra con timestamp y motivo.
  • Puedo consultar el historial completo de una reserva desde la UI.
