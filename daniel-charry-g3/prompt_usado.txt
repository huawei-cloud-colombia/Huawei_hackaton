PROMPT #3 — Definición de arquitectura
================================================================================
Fecha: 2026-09-17
Archivo de referencia: Retos/RETO_3_NEXUS_LIVE.md

Prompt:
  "Basado en el reto Retos/RETO_3_NEXUS_LIVE.md, define una arquitectura para
   implementar un motor de reservas de alta concurrencia que garantice que un
   asiento nunca se venda a dos compradores. El stack debe ser Python + FastAPI."

Decisión del equipo:
  - Stack: Python 3.11 + FastAPI + Uvicorn
  - Concurrencia: asyncio.Lock por asiento (mutex granular)
  - Idempotencia: diccionario Idempotency-Key → resultado cacheado
  - Almacenamiento: en memoria (dict) con expiración por background task
  - Pagos: mock con probabilidades configurables + Circuit Breaker
  - Trazabilidad: lista de eventos auditables
  - Interfaz: HTML + JavaScript servida por FastAPI

Resultado:
  - Arquitectura definida y documentada en README.md.

NOTAS ADICIONALES
================================================================================

- Decisiones donde el equipo NO siguió la primera recomendación del modelo:
  * GLM sugirió usar Redis para el lock distribuido. Decidimos usar
    asyncio.Lock en memoria porque el reto pide una solución demostrable
    localmente y no requiere distribución real.

- Errores encontrados con ayuda del agente:
  * Race condition inicial: el lock por asiento no protegía la operación
    atómica de reservar múltiples asientos. Se corrigió con un lock global
    durante la validación+reserva del conjunto completo.

- Prompts que permitieron resolver problemas importantes:
  * El prompt sobre idempotencia ayudó a entender que el conflicto debe
    comparar el payload normalizado (no solo el JSON string).
